# Project Rules

These rules are mandatory unless explicitly superseded by a later architecture decision.

## Rule 1 — Logical state is authoritative

Never derive puzzle state from rendered mesh transforms.

`CubeState` is authoritative.

---

## Rule 2 — Exactly 26 visible cubies

The logical 3×3 volume contains 27 positions.

The center position:

```text
(0, 0, 0)
```

must remain empty of a visible cubie.

Do not create a fake 27th visible cube.

---

## Rule 3 — Centers are real cubies

The six face centers are visible and remain part of the 26 cubies.

The empty internal position is not a face center.

---

## Rule 4 — No sticker randomization

Never create a scramble by randomly assigning colors to faces.

Every scramble must be generated by legal Rubik moves.

---

## Rule 5 — Renderer never decides legality

The renderer displays a move.

The move engine decides whether and how that move changes state.

---

## Rule 6 — One move at a time

Only one logical face turn may be committed at a time.

Automatic scramble animation uses a queue.

A new move cannot corrupt an active move.

---

## Rule 7 — Animation and state are synchronized

A move has:

1. intent
2. validation
3. animation
4. commit
5. history update
6. solved check

Do not update history before the move is guaranteed to commit.

---

## Rule 8 — Input locking

During an automatic scramble, disable manual cube-turn input.

Camera controls may remain enabled if implementation can safely separate them.

---

## Rule 9 — No decorative cube animation

Cubies may only animate because of a cube operation.

Do not add:

- bounce
- wobble
- glow
- particles
- idle spin
- floating
- elastic scale

---

## Rule 10 — Camera is separate from cube

Orbit and zoom manipulate the camera only.

They must never modify cube coordinates or cubie orientation.

---

## Rule 11 — Face colors are configuration

Color values must be centralized.

Do not hard-code color literals throughout components.

---

## Rule 12 — Responsive first

No critical feature may depend on a single screen size.

---

## Rule 13 — Preserve solvability

Every reachable state must be a state obtainable from the solved cube through legal moves.

---

## Rule 14 — Deterministic testing

The move engine must accept a deterministic sequence.

Example:

```text
R U R' U'
```

should always produce the same state.

---

## Rule 15 — Reset means clean session

Reshuffle must:

- generate a fresh legal scramble
- reset player history
- clear completion state
- leave the cube playable

---

## Rule 16 — Accessibility

All controls must have:

- visible or programmatic labels
- keyboard access where applicable
- sufficient hit area
- focus state
- reduced-motion compatibility

---

## Rule 17 — No hidden state mutation

UI components must not silently modify the cube state.

State mutations must go through the cube domain layer.

---

## Rule 18 — Do not optimize away correctness

Performance improvements must not alter move correctness.

Correct cube behavior has priority over rendering tricks.

---

## Rule 19 — Document architectural exceptions

If an implementation intentionally breaks a rule, document:

- reason
- scope
- risk
- alternative considered

---

## Rule 20 — No implementation before the state model is defined

Do not begin UI polish while the cube move engine is still ambiguous.
